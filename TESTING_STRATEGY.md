# Стратегія тестування – Shear.ly

## 1. Рівні тестування

### Модульне тестування

Перевіряє окремі функції та модулі ізольовано: валідацію URL, сервіси посилань, механізм повторних спроб і middleware.

**Інструменти:** Vitest, mock-об'єкти.

### Інтеграційне тестування

Перевіряє взаємодію маршрутів Express, контролерів, сервісів, репозиторіїв, PostgreSQL і RabbitMQ. Охоплює HTTP-відповіді, обробку помилок і роботу з даними.

**Інструменти:** Vitest, Supertest.

### Контрактне тестування

Перевіряє відповідність компонентів узгодженим інтерфейсам: REST API, форматам відповідей, повідомленням RabbitMQ та gRPC-повідомленням, визначеним у Protocol Buffers.

## 2. Тестування міжсервісної взаємодії

Shear.ly використовує REST API для обробки запитів, PostgreSQL для зберігання даних, RabbitMQ для асинхронного обміну подіями та gRPC для взаємодії з Analytics Service.

Під час тестування необхідно перевіряти:

- Методи REST API, HTTP-статуси, структуру відповідей і заголовки перенаправлення.
- Операції з базою даних та обробку помилок.
- Формат подій RabbitMQ, публікацію повідомлень і роботу споживача.
- Формати gRPC-запитів і відповідей, а також обробку помилок.

Для ізольованих тестів використовуються mock-об'єкти. Для перевірки реальної взаємодії з інфраструктурою потрібні окремі тестові екземпляри PostgreSQL і RabbitMQ.

## 3. Реалізація контрактного тесту

Контрактний тест REST API перевіряє основні умови:

1. `POST /links` повертає статус HTTP 201 і дані створеного посилання.
2. `GET /links/:id` повертає статус HTTP 200 і дані посилання.
3. `GET /links/r/:shortCode` повертає статус HTTP 302 із правильним заголовком `Location`.
4. Під час перенаправлення викликається публікація події про перехід із коротким кодом і correlation ID.

Тест реалізується за допомогою Vitest і Supertest. Репозиторії та publisher імітуються за допомогою mock-об'єктів. Тест перевіряє контракт REST API та виклик publisher, але не підтверджує фактичну доставку повідомлення через RabbitMQ або його обробку Analytics Service.

## 4. Запуск тестів і CI

Основні команди перевірки проєкту:

```bash
npm test
npm run build
npm run test:coverage
```

CI-процес має виконувати перевірку стилю коду, компіляцію TypeScript, автоматизовані тести, формування звіту про покриття та аналіз якості коду.

Цільовий показник загального покриття тестами – не менше 80%.

## 5. Ізоляція тестів

Тести мають бути відтворюваними та незалежними один від одного. Зовнішні залежності слід імітувати там, де це доречно, а mock-об'єкти очищати між тестами. Для інтеграційної перевірки бази даних і черги повідомлень необхідно використовувати окреме тестове середовище. Використання виробничих даних і облікових даних заборонено.
